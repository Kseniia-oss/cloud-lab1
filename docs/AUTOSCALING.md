# Автоматичне масштабування Tasks API

ECS Service Auto Scaling керує `DesiredCount` сервісу `tasks-api`. Політика target tracking у [infra/autoscaling.tf](../infra/autoscaling.tf) тримає середнє використання CPU біля 60%. Межі під час основного експерименту становлять від 1 до 3 завдань Fargate. На рівні 60% залишається запас процесора на короткі піки та запуск нових контейнерів. Для сервісу, який переважно очікує RDS, CPU може недооцінювати навантаження. У такому разі придатна альтернативна метрика `ALBRequestCountPerTarget`.

Cooldown після додавання становить 60 с, а після вилучення 180 с. Це інтервали стабілізації після дій масштабування. За нульового значення політика могла б реагувати частіше, посилюючи коливання кількості завдань. Оцінювання метрики та запуск контейнерів і далі потребували б часу. Під час rolling deployment звичайне вилучення завдань політикою призупиняється, тому вимірювання слід починати після стабілізації сервісу.

| Графік CloudWatch | Що показує |
|---|---|
| ECS DesiredTaskCount і RunningTaskCount | Скільки завдань ECS прагне мати та скільки вже виконується |
| ECS CPUUtilization | Середня частка CPU завдань за хвилину і лінія цілі 60% |
| ALB RequestCount | Сума запитів за хвилину |
| ALB TargetResponseTime p95 | Час від передачі запиту в target до початку відповіді, у секундах |
| ALB та target 5xx | Кількість серверних помилок окремо від ALB та застосунку |

Джерела метрик — AWS/ECS, ECS/ContainerInsights та AWS/ApplicationELB. Додатковий графік RDS використовується для порівняння режимів кешу. Посилання на панель повертає `terraform -chdir=infra output -raw dashboard_url`.

Після перетину CPU 60% CloudWatch має зібрати достатньо точок для оцінювання. Потім ECS планує завдання, Fargate завантажує образ і ALB очікує успішної перевірки здоров’я. При спаді навантаження scale-in потребує стійкого падіння метрики та враховує cooldown. Вилучення target із ALB дає поточним запитам час завершитися.

## Результат хмарного прогону

Після запуску додай знімки панелі з позначеними моментами в UTC. Для scale-out і scale-in зафіксуй бажану та фактичну кількість завдань, щоб показати затримку між рішенням і виконанням.

| Подія | Час UTC |
|---|---|
| Початок сценарію | Очікує вимірювання |
| Перший перетин CPU 60% | Очікує вимірювання |
| Поява нового Running task | Очікує вимірювання |
| Вилучення task і повернення до 1 | Очікує вимірювання |
