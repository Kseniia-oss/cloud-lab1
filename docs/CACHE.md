# Cache-aside у GET /tasks

Застосунок спочатку шукає список у пам’яті процесу за ключем `(user.id, done)`. Якщо запис актуальний, віддає його з `X-Tasks-Cache: HIT`. Інакше читає PostgreSQL, зберігає результат на 45 секунд і позначає відповідь `MISS`. Після вимкнення кешу відповідь позначається `BYPASS`. Кеш має обмеження 256 списків на процес і звільняє найдавніший з погляду використання запис. Авторизація відбувається перед читанням кешу, а перевірка користувача так само звертається до БД.

Локальні копії в різних ECS tasks прогріваються незалежно та можуть повертати різні версії списку. Після створення, редагування або видалення задачі попередній список може бути видимим до 45 с. Щоб скоротити цей час, спільний Redis може зберігати версію списку користувача. Після успішного коміту запису застосунок збільшує версію, а читач використовує новий ключ. Це також захищає від конкурентного запізнілого заповнення старого ключа.

| Метрика | Без кешу | З кешем |
|---|---:|---:|
| p95 усіх HTTP запитів, мс | — | — |
| p95 GET /tasks, мс | — | — |
| HTTP запитів/с | — | — |
| RDS середній CPU під час сталого навантаження, % | — | — |
| RDS середні ReadIOPS під час сталого навантаження | — | — |
| Запитів списку до БД на 100 успішних GET /tasks | 100 за схемою обробки | — |
| Частка HIT серед успішних GET /tasks | Режим BYPASS | — |

Підрахунок `HIT / (HIT + MISS)` робить k6. Оскільки `MISS` і `BYPASS` виконують SELECT списку, їхня частка показує, скільки таких SELECT припадає на 100 успішних запитів цього маршруту. RDS CPU та ReadIOPS зніми за однакову п’ятихвилинну фазу кожного реального тесту. ReadIOPS вимірює читання зі сховища, тому результат також залежить від буфера PostgreSQL, кількості записів і пропускної здатності сценарію.
