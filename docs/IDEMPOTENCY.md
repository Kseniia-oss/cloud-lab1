# Ідемпотентність POST /tasks

Клієнт надсилає `Idempotency-Key`, коли може знадобитися безпечний повтор того самого запиту після timeout або втрати відповіді. Простір ключів окремий для кожного користувача. Повтор із тим самим ключем і тілом повертає збережену відповідь `201`. Якщо тіло змінилося, API повертає `409`. Запити без заголовка працюють за звичайним сценарієм створення.

Redis у приватній мережі зберігає результат до 24 годин від першого успішного запису. PostgreSQL атомарно фіксує задачу і квитанцію. Транзакційне блокування усуває гонку двох одночасних запитів. Якщо процес упаде після коміту або Redis тимчасово недоступний, повтор отримає ту саму відповідь із квитанції. Після закінчення TTL той самий ключ може створити новий запис. Для довготривалої експлуатації прострочені квитанції слід видаляти регулярним фоновим завданням.

У [черзі](QUEUE.md) worker використовує аналогічну транзакційну квитанцію за ID повідомлення. У синхронному маршруті ключ надає клієнт для повтору HTTP-запиту. У маршруті черги ключ отримує worker із повідомлення, щоб SQS міг доставляти його повторно без дублювання ефекту.

## Перевірка

Тест `test_idempotency_replays_same_result_across_concurrent_requests` запускає два конкурентні POST, порівнює тіла відповідей, рахує записи для нового користувача у PostgreSQL та підміняє Redis тестовим об’єктом. Для AWS ввімкни `enable_idempotency=true`. Після деплою повтори тест зі свіжим тестовим користувачем, двічі виконавши `POST /tasks` з однаковим `Idempotency-Key` і тілом. Зроби це з вимкненим кешем списку або дочекайся TTL перед `GET /tasks`, щоб побачити рівно одну задачу. Для звіту зафіксуй відповіді та результат GET. Хмарний Redis має окрему вартість.
